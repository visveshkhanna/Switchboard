title: Secrets and OAuth
description: Keep API keys in the OS keychain, and sign in to remote servers with OAuth.

## Secrets

Servers often need API keys in an environment variable or a header. Rather than writing them into `config.json`, store them as **secrets**: the configuration holds only a reference, `secret://<name>`, and the value lives in your operating system's keychain.

```json
{
  "name": "github",
  "transport": "stdio",
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-github"],
  "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "secret://github-token" }
}
```

A reference works anywhere in a server's `env` or `headers`:

```json
{
  "name": "internal-api",
  "transport": "http",
  "url": "https://mcp.example.com/mcp",
  "headers": { "Authorization": "secret://internal-api-token" }
}
```

When the server starts, Switchboard reads each referenced value from the keychain and passes it to the server. A missing secret stops the server from starting, with an error that names the secret, instead of starting it with an empty value.

Set secret values in the web UI, in the server's environment and header fields. The keychain is:

| OS | Keychain |
|---|---|
| macOS | Keychain |
| Windows | Credential Manager |
| Linux | Secret Service (GNOME Keyring, KWallet) |

Secret values are never written to `config.json` or to logs, and the web UI shows them masked.

## OAuth

Many remote MCP servers sign you in with OAuth instead of an API key. For these, click **Connect** on the server's page in the web UI:

1. Switchboard registers itself with the server's authorization server, using dynamic client registration where it is supported. Otherwise, enter a client ID you created yourself.
2. Your browser opens the sign-in page. The flow uses PKCE, and the redirect comes back to the daemon on `localhost`.
3. The access and refresh tokens are stored in the keychain, like secrets.

Switchboard refreshes tokens before they expire, retrying with backoff if the refresh fails. If a refresh token stops working, the server's status shows it, and **Connect** signs you in again.

Clients never see these credentials: they talk to Switchboard, and Switchboard talks to the server.
